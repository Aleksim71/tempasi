## Текущий статус (на 2026-08-13)

**Каталог полностью укомплектован тестовыми шаблонами:** 30 штук, по
3 на каждую из 10 категорий (`saas-tech-startups`,
`corporate-business`, `healthcare-wellness`, `education-e-learning`,
`portfolio-creative`, `events-weddings`,
`legal-professional-services`, `restaurants-cafes`, плюс ранее —
`ecommerce`, `real-estate`). Каждый — честный HTML/CSS макет (4
страницы: index + 3), синтетические placeholder-изображения без
внешних фото, реальная валидация через `templateZip.contract.cjs`
перед выдачей.

**В процессе наполнения найдено и исправлено несколько реальных
багов в кабинете продавца** (маленькие точечные патчи, все применены
и закоммичены):

- `POST /cabinet/my-templates/:id/delete` вообще не существовал —
  кнопка Delete в разметке была, серверной части не было;
  `deleteMyTemplate()` в сервисном слое уже был полностью готов,
  просто не подключён к роуту.
- `POST /cabinet/my-templates/:id/status` (Publish/Unpublish) —
  роут существовал, но без `express.urlencoded()` — `req.body` был
  всегда `undefined`, кнопки молча ничего не делали.
- Категория сбрасывалась в пустой список при перерендере формы Add
  после ЛЮБОЙ другой ошибки валидации — `GET`-путь передаёт
  `categoryOptions` в шаблон, `POST`-путь (error-branch) — не
  передавал.
- Превью шаблонов не показывались на публичном профиле в Community

  (тем самым фолбэком, которым давно пользуется основной каталог).
- `TEMPLATE_CATEGORY_VALUES` (см. "Известный долг" ниже) —
  практическая часть бага закрыта, не трогая сам хардкод-список.
- Редкая гонка при создании шаблона: `SLUG_ALREADY_EXISTS` (путь
  Add) и `SLUG_TAKEN` (путь Edit) — разные имена ошибки для одного и
  того же конфликта уникальности `slug`; Add-путь проверял только
  `SLUG_TAKEN`. Добавлен ретрай с перегенерацией slug (до 3 попыток)
  - понятное сообщение на случай, если все ретраи всё равно
    столкнутся.
- **Реальная миграция БД, уже применена на рабочей базе:**
  `seller_templates_slug_unique` был обычным `UNIQUE CONSTRAINT` на
  всю таблицу без исключения для мягко удалённых строк — удалённый
  шаблон навсегда занимал свой slug, хотя код-проверка "свободен ли
  slug" уже корректно игнорировала `deleted_at`-строки. Заменено на
  частичный `UNIQUE INDEX seller_templates_slug_unique ON
seller_templates (slug) WHERE deleted_at IS NULL`. **Это изменение
  схемы не отражено ни в одном файле миграции** (см. пункт про файлы
  миграций в Части 4) — учитывать при следующем `\d
seller_templates`.
- UX: ошибки формы Add/Edit Template теперь показываются в модалке
  вместо мелкого текста под полем/наверху страницы — переиспользован
  modal-шелл из flow аренды (`window.TempasiModal`, был приватным в
  `core.js`, теперь экспортирован), заголовок красным "Error!"
  (`var(--c-danger)`).

**Каталог: серверная фильтрация + пагинация (новая сессия,
2026-08-13).** `GET /templates` раньше отдавал сразу все опубликованные
шаблоны (`LIMIT 200`), а фильтрация (`cat`/`q`/`access`/`priceMax`)
была чисто клиентской — JS прятал/показывал уже отрисованные SSR-карточки
в DOM. Решение принято с горизонтом роста каталога до ~5000 шаблонов
(1000 студий x 5 шаблонов, ориентир — 2,5 года), при котором клиентская
DOM-фильтрация деградирует.

- **`selectTemplatesForCatalogPage(db, filters, pagination)`** — новая
  функция в `templates.repo.js`, фильтрация теперь в SQL (`WHERE` по
  `category`/`price_buy_cents`/`title`+`slug` ILIKE), `LIMIT`/`OFFSET`
  - отдельный `COUNT(*)` для тотала. Старая `selectTemplatesForCatalog(db)`
    **не тронута** (сигнатура и поведение те же, всё ещё `LIMIT 200` без
    пагинации) — на неё завязаны 4 теста, которые сканируют весь каталог
    напрямую через repo (`catalog.rent-visibility`, `rentExpiration`,
    `pendingRentCheckout`, `failedCancelledExpiredRentCheckout`).
- **UX-решение (осознанный выбор, не default):** классический GET с
  перезагрузкой страницы, а не AJAX без перезагрузки. Причина —
  риск-профиль этого проекта (см. "Часть 4", урок про потерю кода при
  full-file-overwrite патчах в чувствительных файлах каталога) важнее
  сохранения прежнего мгновенного UX. Чекбоксы категорий / radio
  Access / селектор "На странице" — auto-submit по `change`. Поиск и
  цена — применяются по кнопке Apply / Enter, не на каждый
  keystroke/пиксель ползунка (иначе дёрганые перезагрузки).
- **"На странице": 10/20/30, селектор для пользователя** (не фикс),
  номера страниц (не Prev/Next, не "load more").
- `priceActive` — отдельный скрытый флаг, отличает "ползунок стоит на
  дефолтных $250 просто визуально" от "юзер реально его подвинул" —
  так же вело себя и старое клиентское решение, сохранили поведение.
- `public/js/templates.catalog-filters.js` переписан с нуля: больше не
  DOM show/hide, а auto-submit + визуальная синхронизация
  ползунок↔число.
- Патч применён через `git apply` (реальный unified diff, не
  full-file-overwrite) — сгенерирован и провалидирован (dry-run +
  post-apply verify) на чистой копии архива перед отправкой.

## Текущий статус (на 2026-08-14) — бэкапы, восстановление, симуляция покупок

Огромная сессия, три больших связанных трека. Патчи применялись
файловым способом (`git apply` + `run.sh` с pre-flight/dry-run/verify)
на реальном актуальном снапшоте архива, не на реконструкции.

### Часть A — Бэкапы

- **`scripts/backup-templates.sh`** — git-инкрементальный бэкап
  `TEMPLATE_UPLOAD_DIR` (старичок) → `Archiv-11/tempasi-templates-backup`
  (git-репозиторий, каждый прогон = коммит, только реальные изменения).
  `rsync` **без** `--delete` — удаления с source не долетают до
  бэкапа намеренно (backup, переживающий удаления, — весь смысл).
  Двойная mount-safety проверка (source + destination) через
  `st_dev`-сравнение.
- **`scripts/backup-db.sh`** — `pg_dump | gzip`, ротация 7 последних
  дампов, `.tmp`-файл + переименование только после успеха
  (`trap`-based cleanup — реальный баг с "битым `.tmp` при падении
  `pg_dump`" пойман и починен в процессе).
- **`scripts/backup-full.sh`** — объединённый режим: шаблоны → git
  commit hash → дамп БД → манифест (`{dbDump, templatesBackupCommit}`)
  рядом с дампом. **Без даунтайма** — сознательное решение вместо
  изначальной идеи с 10-минутным техобслуживанием (`pg_dump` и так
  атомарен, rsync только читает/копирует). Манифест — не полный
  файл-архив каждую ночь (git-история шаблонов и так всё хранит),
  а лёгкая пара "какой дамп + какой коммит".
- **Admin → Settings → Backup** — toggle Enable/Disable автобэкапа
  (флаг-файл `.backup-automatic-disabled`, в `.gitignore`) + кнопка
  "Run backup now" (синхронный запуск `backup-full.sh --force`).
- **`scripts/cleanup-orphaned-templates.cjs`** — сверяет живую БД
  (`seller_templates WHERE deleted_at IS NULL`) со старичком и
  бэкапом, удаляет "осиротевшие" файлы (в т.ч. то, что ещё лежит в
  Trash, но уже не активно) — с двух сторон: старичок (`rm`,
  необратимо) и бэкап (`git rm` + commit, восстановимо). Перед
  удалением сам гоняет свежий `backup-templates.sh` как страховку.
  **Реальный баг найден и починен**: mount-проверка изначально шла по
  подпапке внутри диска вместо самого диска — подпапка всегда имеет
  тот же `st_dev`, что и родитель, поэтому ложно ругалась "не mount"
  даже когда диск реально подключён.

### Часть B — Восстановление

- **`scripts/restore-full.sh <dump> [--exact]`** — единственный
  CLI/detached-скрипт, откатывающий **БД+шаблоны всегда парой** (по
  манифесту). БД — всегда полная пересборка схемы
  (`DROP SCHEMA public CASCADE` + накат дампа), частичный откат
  реляционных данных не имеет смысла. Шаблоны — два режима:
  `additive` (по умолчанию, ничего не удаляет) и `--exact` (точное
  соответствие снепшоту, удаляет лишнее — на случай подозрения на
  порчу файлов на старичке).
- **`src/server.js`** — пишет `.server.pid` при старте, graceful
  shutdown по `SIGTERM` (нужно скрипту восстановления, чтобы
  аккуратно остановить текущий процесс перед накатом БД и потом
  поднять новый — без pm2/systemd, скрипт сам себе supervisor на
  разовую операцию).
- Кнопка **Restore** в админке — только для снепшотов с манифестом,
  подтверждение — **точное имя файла дампа** через `window.prompt()`
  (строже, чем просто слово, как в Danger Zone), проверяется и на
  клиенте, и на сервере. `spawn(..., {detached: true}).unref()` —
  HTTP-ответ уходит до того, как сам процесс убьёт себя.
- **Реальный баг найден на первом же настоящем прогоне**: `mktemp -d`
  создаёт scratch-папку с правами `700`; `rsync -a` — вопреки
  ожиданиям, что trailing slash защищает корень назначения — всё
  равно переносит права корня SRC на корень DST. Итог: права
  `/mnt/tempasi/templates` (и его зеркала на старичке,
  `/var/lib/tempasi/templates`) упали до `700`, `www-data` (nginx)
  потерял доступ, посыпались 403 на превью/демки. Пофикшено (даём
  scratch-папке `755` + явно восстанавливаем исходные права
  назначения после rsync) и подтверждено на живой инфраструктуре.

### Часть C — Симуляция покупок (эксклюзивность BUY)

Три взаимосвязанных решения по итогам обсуждения (полная история — в
чате, не дублирую здесь):

1. **Убран cart-hold из каталога.** Раньше просто добавление в
   корзину **навсегда** (без TTL) прятало шаблон из каталога — юзер
   мог закинуть весь каталог в корзину и уехать в Турцию, обездвижив
   площадку. Теперь корзина ничего не блокирует; эксклюзивность
   держится только на факте **оплаченной** покупки.
2. **Гонка при двойной продаже** — оказалось, уже полностью
   защищена с прошлых сессий: partial unique index
   `orders_unique_paid_buy_per_template` в БД (миграции
   `20260302_0001` + `20260406_0002`, подтверждено `\di` на живой
   базе) + обработка `23505` в `orders.repo.cjs`. Ничего не
   писали — только нашли и подтвердили.
3. **UX "already sold"** — раньше голый `409 BUY already sold for:
slug` без стилизации. Теперь: `assertBuyExclusivity()` кидает
   `code: 'BUY_ALREADY_SOLD'` + `soldSlugs`, роут убирает позицию из
   корзины и редиректит на `/cart` с понятным баннером.
4. **Новая кнопка "Checkout"** на `/cart` — обрабатывает **все**
   BUY-позиции разом через настоящий пайплайн
   (`ordersService.createOrderCheckout()` +
   `PaymentCompletion.completePaidOrder()` на каждую позицию — те же
   функции, что и у настоящего вебхука), с `confirm()` перед
   отправкой (количество + сумма). Ссылка на скачивание на итоговой
   странице. Старая "Complete demo checkout" (отдельная, самописная
   raw-SQL реализация мимо `completePaidOrder()`) осталась, но
   помечена как legacy/без подтверждения — сознательно не тронута
   до явного решения, что с ней делать.
5. **Реальный баг найден на первом настоящем прогоне новой кнопки**:
   `cart_items.license` для BUY хранит `'BUY'` (это deal type, не
   тир лицензии — наследие от скрытого поля в кнопке каталога).
   `normalizeBuyPayload()` в `orders.service.cjs` ждёт реальный тир
   (`PU`/`CU`/`EL`/`ML`/`EX`) и справедливо падал с `INVALID_LICENSE`.
   Старый raw-SQL путь этого не проверял вообще, поэтому баг был не
   виден. Пофикшено — хардкод `license: 'PU'`, как и в уже рабочем
   `/checkout/direct/buy/:slug/pay`.
6. **Ещё один реальный баг, ортогональный всему вышеперечисленному**:
   миграции `20260428_0003_account_credits.sql` и
   `20260428_0004_account_credit_checkout_usage.sql` существовали в
   репозитории с прошлой сессии, но **никогда не были накатаны** на
   реальную БД. Настоящий пайплайн оплаты (`completePaidOrder()`)
   безусловно обращается к таблице `account_credit_usages` —
   `relation does not exist` вылезло на первой же настоящей покупке
   через новую кнопку. Накатаны вручную через `psql`/`\i`. **Это
   касается вообще любой настоящей покупки, не только новой кнопки**
   — стоит проверить, нет ли ещё где-то написанных, но не
   применённых миграций (см. долг ниже).

**RENT в новой кнопке не поддержан** — у `cart_items` физически нет
колонки `rent_days` (срок аренды сейчас нигде в корзине не хранится).
RENT-позиции при массовом чекауте честно пропускаются, остаются в
корзине с пометкой "check out individually".

## Известный долг

- **`TEMPLATE_CATEGORY_VALUES`** в `sellerTemplates.service.cjs` —
  хардкод-список из 11 старых категорий, всё ещё существует
  намеренно как safety-net для мусорного ввода в
  `normalizeTemplateCategory()`. Практический баг (новая категория,
  добавленная через админку, откатывалась на "Other" при СОЗДАНИИ
  шаблона) закрыт отдельной live-проверкой против
  `catalog_categories` поверх этой функции — сам хардкод-список
  сознательно не тронут, самый чувствительный путь в файле.
- **Открытый вопрос с Этапа 2:** у `seller_templates` нет состояния
  "на модерации" — решить, добавлять ли `pending`-статус или делать
  постмодерацию поверх `draft`/`published`.
- **Каталог: индексы под фильтры не добавлены (пока не нужно).**
  `GET /templates` фильтрует и пагинирует на сервере — `WHERE` по
  `category`/`price_buy_cents`/`title`/`slug` без индексов на этих
  колонках. При ~32 шаблонах не критично. Вернуться и добавить
  `CREATE INDEX`, когда каталог разрастётся (ориентир — до ~5000 за
  2,5 года).
- **⚠️ Возможны другие написанные, но не накатанные миграции.**
  `20260428_0003`/`20260428_0004` (account credits) пролежали в
  репозитории с прошлой сессии, ни разу не применённые к реальной
  БД — обнаружилось только когда реальный пайплайн оплаты впервые
  дошёл до кода, который их использует. Стоит когда-нибудь пройтись
  по всем файлам в `src/db/migrations/` и явно сверить с
  `information_schema` на living БД, какие реально применены, а
  какие только лежат как намерение. Нет раннера/таблицы учёта
  миграций — все накатываются вручную через `psql -f`/`\i`, отсюда и
  риск таких пропусков.
- **"Complete demo checkout"** (`/cart/demo-checkout`,
  `demoCompleteCartCheckout()` в `cart.routes.js`) — отдельная,
  самописная raw-SQL реализация покупки, идущая мимо
  `completePaidOrder()`. Оставлена как legacy/без подтверждения,
  сознательно не тронута. Решить в будущем: убрать совсем (только
  новая кнопка "Checkout"), или доработать под что-то своё
  (например, единственный путь, поддерживающий множественные позиции
  до того, как это доделали в новой кнопке — актуальность уже под
  вопросом).
- **RENT не поддержан в массовом Checkout** — `cart_items` не хранит
  `rent_days`, поэтому RENT-позиции при клике "Checkout" пропускаются
  и остаются в корзине. Если понадобится тестировать RENT-сценарии
  массово — сначала нужно научить корзину хранить срок аренды.
- **`/checkout/direct/buy/:slug/pay`** (путь из карусели Cases
  workspace, не из основного каталога) — при ошибке (`TEMPLATE_ALREADY_SOLD`
  и т.п.) редиректит на `/templates?buy_error=CODE`, но этот
  query-параметр нигде не рендерится в сообщение — юзер просто
  попадает на каталог без объяснения. Отдельный, самостоятельный баг,
  не по основному пути покупки — не трогали сегодня.
- **Инфраструктурная заметка**: за сегодняшнюю сессию несколько раз
  ловился баг двойного экранирования `\u2014`/`\u20ac`/`\u2705` при
  использовании `str_replace`-эскейпов внутри правок — инструмент
  задваивал обратный слэш. Впредь безопаснее сразу вставлять реальные
  UTF-8-символы (тире, евро, эмодзи) в патчи вместо `\uXXXX`-эскейпов,
  независимо от типа файла (JS/bash/Handlebars) — во всех трёх было
  словлено и починено сегодня.

## Часть 2. Правила работы (актуально)

### Режимы

- **Обсуждение** — просто разговариваем, ничего не меняем в проекте.
- **Работа** — берём одну маленькую цель, доводим до конца по шагам
  ниже, проверяем, только потом берём следующую.

### Порядок работы над одной целью (обязателен)

1. **Сбор информации** — реальные файлы/схема БД/конвенции, не
   предположения.
2. **Варианты решения** — привязаны к реальному коду.
3. **Обсуждение и выбор.**
4. **Реализация** — патч (файлы/SQL/тесты).

### Изоляция админки (MVP на том же сайте, задел на отделение)

- Код/вьюхи — только в своих namespace'ах:
  `src/web/routes/admin.*.routes.cjs`,
  `src/web/middleware/require-admin.web.js`,
  `src/web/views/pages/admin/*`, `public/css/pages/admin*.css`.
- Визуал — исключение: header/footer/шрифты сознательно общие с
  публичным сайтом. Изоляция — только код/бизнес-логика.
- Админка не пишет ad-hoc SQL по таблицам других модулей — операция
  добавляется как метод в сервис модуля-владельца.
- Известный компромисс: авторизация админки использует общие
  `sessions`/`users`. При реальном отделении — общий session-store
  (Redis) или SSO. Не блокер сейчас.

### Обмен файлами

```
incoming   <- патчи от Claude (в этом чате: /home/aleksim/Загрузки)
outgoing   <- результаты/логи от пользователя обратно Claude
archive    <- применённые патчи (история)
```

Проект: `/home/aleksim/tempasi`.

### Формат патча

- Единая точка входа — `run.sh` (bash, Ubuntu), применяет всё, пишет
  лог в `outgoing/`.
- Изменения в БД — отдельный `.sql` + `pg_dump`-бэкап + явное
  подтверждение перед деструктивными операциями.
- **Перед любой full-file-overwrite правкой** — грепнуть целевой файл
  на 2-3 маркера уже известных прошлых фич; если хоть один не найден
  — остановиться, восстановить из сохранённых `patchN` или запросить
  свежий `tempasi.zip`. См. урок про потерю кода ниже.
- **Патчи с зависимостями друг от друга** (например, категорийный
  фикс требует уже применённого delete-фикса в том же файле) —
  `run.sh` каждого такого патча грепает маркер патча-предпосылки в
  начале и падает с понятным ABORT, если его нет. Несколько патчей
  за сессию подряд по одному и тому же файлу — это нормально, не
  повод сливать всё в один патч.

### Правило "Пилигрима"

- Загружается в начале чата (`docs/PILGRIM.md`, без даты — всегда
  актуальная точка входа).
- Обновляется Claude в конце чата.
- Периодически архивируется целиком под датой, когда разрастается —
  см. раздел "Архивы" в начале этого файла.
- Новый чат — по достижении естественной паузы или ~20 сообщений,
  пользователь отслеживает сам.

### Технические детали окружения

- ОС/шелл: Ubuntu, bash. Проект под git, ветка
  `feat/analytics-kpi-summary`.
- Доступ к БД: через `.env` (`DATABASE_URL`), `psql` тоже доступен
  напрямую в терминале пользователя.
- Стек: Node.js/Express 5, PostgreSQL, Handlebars (SSR), CJS-модули
  вперемешку с ESM (`.cjs` vs `.js` — смотреть по факту в каждом
  файле), git, `getPool()` для доступа к БД.

## Часть 4. Устойчивые уроки (актуально, перечитывать каждую сессию)

- **`node --check` проверяет только синтаксис, не то, что нужный
  export реально существует.** Если патч добавляет/переносит функцию
  в `module.exports` — перед отправкой реальный `require()`
  собранного файла (с заглушками зависимостей при необходимости) и
  явная проверка `typeof mod.functionName === 'function'`.
- **ПОВТОРЯЮЩИЙСЯ РИСК (7+ подтверждённых случаев за прошлые сессии,
  включая 3 подряд с одним и тем же файлом): песочница Claude
  периодически теряет файлы между сообщениями чата, полная
  перезапись файла на основе устаревшей копии молча откатывает уже
  закоммиченную работу.** Особенно уязвимые файлы (накопили больше
  всего несвязанных правок за сессии): `admin.pages.routes.cjs`,
  `cabinet.pages.routes.cjs`, `sellerTemplates.service.cjs`/`.repo.cjs`.
  **Правило:** для файлов из этого списка — не полагаться на
  "маленькая правка, ничего не потеряется"; грепать 2-3 маркера
  прошлых фич перед full-file-overwrite (см. также "Формат патча"
  выше). Подробности всех случаев — в архиве.
- **Файлы миграций в этом репо НЕЛЬЗЯ считать источником истины про
  реальную схему БД.** Раннера миграций нет, на прод накатывается
  вручную, миграции систематически расходятся с реальностью (минимум
  6 подтверждённых случаев, включая частичный уникальный индекс на
  `seller_templates.slug` от 2026-08-13). **Правило: прежде чем
  полагаться на список допустимых значений/структуру таблицы —
  `\d <table>` на реальной БД, не файл миграции**, если вопрос хоть
  немного важен (тем более деньги/чекаут).
- **Разные имена ошибки для одного и того же конфликта, брошенные из
  функций-сестёр — повторяющийся источник багов.** Конкретный
  случай: `insertSellerTemplate` кидает `SLUG_ALREADY_EXISTS`,
  `updateSellerTemplate` кидает `SLUG_TAKEN` для семантически той же
  ситуации (уникальность slug), роут проверял только один из двух.
  При добавлении обработки ошибки от функции в `*.repo.cjs` — грепать
  все места, где эта функция (и её "родственники" по смыслу) реально
  кидают `new Error(...)`, а не полагаться на то, что один
  проверяемый код покрывает всё семейство похожих ошибок.
- **HTML `<input type="file">` не восстанавливает выбор при
  перерендере страницы после ошибки валидации** — ни сервер, ни
  клиентский JS не могут заранее подставить туда файл (ограничение
  браузера, не баг). Если форма с файлом падает по НЕ связанной с
  файлом причине (например, дубль slug) и пользователь просто жмёт
  submit ещё раз не выбирая файл заново — получит "ZIP file is
  required" на ровном месте. Не чинить это на уровне кода, но иметь
  в виду при диагностике "почему опять просит файл, я же его уже
  давал".
- **Проверка реального mount'а, не просто `fs.existsSync()`.**
  Директория "существует" не значит "смонтирована" — сравнение
  `st_dev` директории и родителя (`isMountPoint()` в
  `templateStorageCheck.cjs`) — тот же приём, что у Unix-команды
  `mountpoint`. Актуально для любой будущей интеграции с внешними
  примонтированными хранилищами.
- **Решение:** админка встроена в существующее приложение (роль
  `admin`/`superadmin` в общей таблице `users`), не отдельный сайт —
  общие таблицы `users`/`sessions`, стадия MVP.
- **Решение:** визуал админки полностью переиспользует публичный
  дизайн (header/footer/шрифты). Изоляция — только код/данные.
- **Риск:** таблица `users` не создаётся ни одной миграцией в
  `src/db/migrations/` — схема известна только из
  `tests/helpers/migrateDb.cjs`. `orders.amount_cents` в том же
  положении.
