## Текущий статус (на 2026-08-16)

Огромная двухдневная сессия (2026-08-15/16). Единый переиспользуемый
UI-паттерн сообщений по всему сайту, полный перевод на английский,
консистентные табы, мягкое удаление аккаунтов (само- и админом), и
полная перестройка Analytics (Overview/Advanced/Table). Все патчи —
файловым способом (`git apply` + `run.sh` с pre-flight/dry-run/verify)
на реальном актуальном снапшоте архива.

### Часть A — Единая система модалок

Заменены все 5 нативных `window.confirm()`/`window.prompt()` в
проекте на кастомную стилизованную модалку.

- **`public/js/confirm-modal.js`** — три глобальные функции:
  `window.tempasiConfirm({title, message, confirmLabel, danger})` →
  `Promise<boolean>`, `window.tempasiPrompt({..., inputPlaceholder})`
  → `Promise<string|null>` (контракт как у нативного `prompt()` —
  `null` при отмене, поэтому существующие сравнения
  `typed !== expectedValue` на местах вызова менять не пришлось),
  `window.tempasiAlert({...})` → `Promise<void>` (однокнопочный,
  для информационных сообщений — добавлен позже, когда понадобилось
  показывать серверные `?cart=CODE`-редиректы). Подключён глобально
  в `main.hbs`.
- **`public/css/components/ui-controls-contract.css`** — общий
  контракт кнопок-табов: `.tp-control.tp-tab.tp-tab--main` (жёлтый
  контур, толще+жирный на `.is-active`) и `.tp-tab--sub` (то же самое
  зелёным). Существовал раньше только для Cases card actions —
  распространён на все главные и вложенные табы сайта (Add/List/
  Analytics, Finance, Profile & Security, Support, Analytics
  Overview/Table/Advanced).
- Заменены 6 "голых" HTML-страниц (`res.send('<!doctype html>...')`
  без header/footer) на рендер через обычный `res.render()` —
  новый шаблон `pages/standalone-message.hbs` +
  хелпер `renderStandalonePage()`. Не тронут намеренно: fallback в
  `creditLedger.controller.cjs` — это safety-net на случай падения
  основного рендера, переводить его на тот же движок было бы
  контрпродуктивно.
- **Добавлена страница 404** (`Cannot GET /path` → нормальная
  страница с header/footer). **Реальная ловушка, пойманная
  тестом:** 404-catch-all нельзя вешать ни внутри
  `app.web.js#createWebApp()`, ни на внешний `app` в `app.js` —
  `webApp` донавешивает `/cabinet`, `/admin`, `/checkout`,
  `/community` УЖЕ ПОСЛЕ возврата из `createWebApp()`; catch-all
  внутри неё перехватил бы все эти роуты. Также `res.render()`
  внутри catch-all падает с "No default engine", если он висит на
  внешнем `app` — `view engine` настроен только на `webApp`.
  Правильное место — `webApp.use(...)` в конце `app.js`, после ВСЕХ
  остальных `webApp.use(...)`. Подтверждено тестом через реально
  собранный `app.js` (не изолированный `app.web.js`).

### Часть C — Перевод на английский

Изначальная оценка "32 файла с русским текстом" оказалась сильно
раздута ложными срабатываниями `grep -P` на многобайтовые UTF-8
символы (`€`, `—`, `’`) — **урок: для поиска кириллицы использовать
Python с точным unicode-диапазоном `\u0400-\u04FF`, не полагаться на
`grep -P` под некоторыми локалями/системами** (падает с "code point
too large" на синтаксисе `\x{0400}`, либо даёт ложные совпадения).
Реально нашлось и переведено **29 файлов** по всему `src/` (не
только `.hbs`, но и `.js`/`.cjs`/`.sql`-комментарии), затем ещё 6
CSS-файлов отдельным патчем — первый проход не проверял `.css`.

### Часть D — Мягкое удаление аккаунтов

**Самоудаление** (Cabinet → Profile & Security): физического
удаления нет — `users.status = 'deleted'` + `self_deleted_at`.
**Реальная находка, определившая архитектуру**: логин
(`auth.pages.routes.js`) **уже отклонял** вход при
`status !== 'active'` — вентиль был готов, просто ничего никогда не
устанавливало другое значение. Все сессии юзера удаляются
(`DELETE FROM sessions WHERE user_id = $1`), cookie чистится.

**Видимость** — везде, где раньше проверялось
`owner_withdrawn_at IS NULL` и т.п., добавлена проверка через `users
u` / `u.self_deleted_at IS NULL`: каталог (3 функции в
`templates.repo.js`), community (профиль + список), прямая покупка,
`/cart/add`. **Не почищено (шире задачи, отмечено, не тронуто)**:
ни `cart.checkout-pass.service.js`, ни `orders.service.cjs` не
перепроверяют статус продавца в момент самого чекаута — только при
добавлении в корзину.

**Миграция** `20260816_0001_users_self_delete.sql` — добавляет
`self_deleted_at` + `CHECK (status IN ('active', 'deleted'))`
(констрейнта раньше не было вообще). **Реальная регрессия от неё**:
`tests/catalog.rent-visibility.test.cjs` создавал тестового юзера с
`status = 'observer'` (произвольный плейсхолдер с тех времён, когда
констрейнта не было) — починено на `'active'`.

**Admin-удаление любого юзера** — зеркалит паттерн Templates Trash:
кнопка "Delete" в списке Users (только для активных), отдельная
страница `Admin → Users → Trash` со списком удалённых + "Restore".
Никакого "Delete forever" для юзеров (в отличие от шаблонов) — не
просили, каскад по orders/entitlements/seller_templates был бы
самостоятельным большим решением. **Реальный баг, пойманный
тестом**: `safeReturnTo()` был жёстко зашит на `/admin/templates` —
Restore/Delete для юзеров редиректили не туда. Заведён отдельный
`safeUsersReturnTo()`.

### Часть E — Analytics (Cabinet → My Templates → Analytics)

Три вкладки, все три получили реальную (не заглушечную) реализацию:

- **Overview** — **реальный баг**: карточки KPI были полностью
  пустыми — роут строил `summary.*`, шаблон читал `kpis.*`, разные
  имена полей, ничего не совпадало. Починено подключением уже
  существовавших, но никогда не вызывавшихся `getMyTemplatesKpis()`
  - `getPlatformStats()`. Показывает: "My templates" (личные — All,
    Active, Avg. цена продажи/аренды **среди листинга**) и "Market"
    (по всей платформе, то же самое). 30-дневный график убран отсюда
    (переедет в Finance отдельной задачей, сама функция цела).
- **Второй реальный баг, найденный при полировке**: `COUNT(*)
FILTER (...)` в `getMyTemplatesKpis()` считал СТРОКИ после
  `LEFT JOIN orders`, а не уникальные шаблоны — шаблон с несколькими
  заказами задваивался в счётчике. Подтверждено отдельной моделью
  до правки SQL. Везде, где считаются шаблоны — `COUNT(DISTINCT
st.id)`. Заодно "Active templates" раньше означало "просто не
  удалён", без проверки публикации/отзыва/блокировки/продажи —
  теперь использует то же условие видимости, что каталог.
- **Advanced** — та же структура, что Overview, но цены — **не
  листинговые, а реализованные**: средняя цена среди РЕАЛЬНО
  проданных/арендованных (`EXISTS` оплаченный заказ на шаблон,
  использует цену с самого шаблона, не `orders.amount_cents` — так
  не нужно нормализовать многодневную аренду обратно к цене за
  день).
- **Table** — раньше таблица по шаблонам (к тому же тоже тихо
  сломанная — шаблон читал `.items`, роут строил `.topTemplates`).
  Заменена полностью на разбивку **по категориям, по всей
  платформе**: Category → Templates → Avg. sale price → Avg. rent
  price → Avg. sale price (sold) → Avg. rent price (rented).
  Категория остаётся в списке, даже если сейчас 0 активных
  листингов, но раньше что-то продавалось/арендовалось.
- **Устойчивый паттерн всей части E**: для любых `AVG()`-запросов —
  НИКОГДА не через `LEFT JOIN orders` напрямую (fan-out: JOIN
  плодит по строке на каждый заказ, `AVG`/`COUNT(*)` без `DISTINCT`
  считают неправильно). Только `EXISTS`-подзапрос — не плодит строк.
  Использовано в `getMyTemplatesAvgPrices`,
  `getMyTemplatesRealizedAvgPrices`, `getPlatformStats`,
  `getPlatformRealizedAvgPrices`, `getPlatformStatsByCategory`.

**Закоммичено, рабочее дерево чистое, 85 коммитов впереди
`origin/feat/analytics-kpi-summary`** (не запушено). Последний
коммит: `1a0f793` (категорийная таблица).

## Часть 2. Правила работы (актуально)

### Режимы

- **Обсуждение** — просто разговариваем, ничего не меняем в проекте.
- **Работа** — берём одну маленькую цель, доводим до конца по шагам
  ниже, проверяем, только потом берём следующую.

### Порядок работы над одной целью (обязателен)

1. **Сбор информации** — реальные файлы/схема БД/конвенции, не
   предположения.
2. **Варианты решения** — привязаны к реальному коду.
3. **Обсуждение и выбор.**
4. **Реализация** — патч (файлы/SQL/тесты).

### Изоляция админки (MVP на том же сайте, задел на отделение)

- Код/вьюхи — только в своих namespace'ах:
  `src/web/routes/admin.*.routes.cjs`,
  `src/web/middleware/require-admin.web.js`,
  `src/web/views/pages/admin/*`, `public/css/pages/admin*.css`.
- Визуал — исключение: header/footer/шрифты сознательно общие с
  публичным сайтом. Изоляция — только код/бизнес-логика.
- Админка не пишет ad-hoc SQL по таблицам других модулей — операция
  добавляется как метод в сервис модуля-владельца.
- Известный компромисс: авторизация админки использует общие
  `sessions`/`users`. При реальном отделении — общий session-store
  (Redis) или SSO. Не блокер сейчас.

### Обмен файлами

```
incoming   <- патчи от Claude (в этом чате: /home/aleksim/Загрузки)
outgoing   <- результаты/логи от пользователя обратно Claude
archive    <- применённые патчи (история)
```

Проект: `/home/aleksim/tempasi`.

### Формат патча

- Единая точка входа — `run.sh` (bash, Ubuntu), применяет всё, пишет
  лог в `outgoing/`.
- Изменения в БД — отдельный `.sql` + `pg_dump`-бэкап + явное
  подтверждение перед деструктивными операциями. Перед CHECK-
  констрейнтами на существующую колонку — сначала `SELECT DISTINCT
  <col> FROM <table>` на реальной БД, констрейнт иначе не
  прикрепится, если есть неожиданное значение (пример: `'observer'`
  в тестовой фикстуре, см. Часть D).
- **Перед любой full-file-overwrite правкой** — грепнуть целевой файл
  на 2-3 маркера уже известных прошлых фич; если хоть один не найден
  — остановиться, восстановить из сохранённых `patchN` или запросить
  свежий `tempasi.zip`. См. урок про потерю кода ниже.
- **Патчи с зависимостями друг от друга** — `run.sh` каждого такого
  патча грепает маркер патча-предпосылки в начале и падает с
  понятным ABORT, если его нет. Несколько патчей за сессию подряд по
  одному и тому же файлу — это нормально, не повод сливать всё в
  один патч.
- **Перед вставкой кода с `—`/`€`/эмодзи через `str_replace`** —
  всегда реальный UTF-8-символ, никогда `\uXXXX`-эскейп (инструмент
  задваивает обратный слэш). Безопаснее — строить такие правки через
  `bash_tool`/Python (`content.replace(...)`) вместо `str_replace`,
  если правка длинная или тире/евро много.

### Правило "Пилигрима"

- Загружается в начале чата (`docs/PILGRIM.md`, без даты — всегда
  актуальная точка входа).
- Обновляется Claude в конце чата.
- Периодически архивируется целиком под датой, когда разрастается —
  см. раздел "Архивы" в начале этого файла.
- Новый чат — по достижении естественной паузы или ~20 сообщений,
  пользователь отслеживает сам.

### Технические детали окружения

- ОС/шелл: Ubuntu, bash. Проект под git, ветка
  `feat/analytics-kpi-summary`.
- Доступ к БД: через `.env` (`DATABASE_URL`), `psql` тоже доступен
  напрямую в терминале пользователя.
- Стек: Node.js/Express 5, PostgreSQL, Handlebars (SSR), CJS-модули
  вперемешку с ESM (`.cjs` vs `.js` — смотреть по факту в каждом
  файле), git, `getPool()` для доступа к БД.

## Часть 4. Устойчивые уроки (актуально, перечитывать каждую сессию)

- **`node --check` проверяет только синтаксис, не то, что нужный
  export реально существует.** Если патч добавляет/переносит функцию
  в `module.exports` — перед отправкой реальный `require()`
  собранного файла (с заглушками зависимостей при необходимости) и
  явная проверка `typeof mod.functionName === 'function'`.
- **ПОВТОРЯЮЩИЙСЯ РИСК: песочница Claude периодически теряет файлы
  между сообщениями чата, полная перезапись файла на основе
  устаревшей копии молча откатывает уже закоммиченную работу.**
  Особенно уязвимые файлы (накопили больше всего несвязанных правок
  за сессии): `admin.pages.routes.cjs`, `cabinet.pages.routes.cjs`,
  `analytics.cabinet.service.cjs`, `space-my-templates.hbs`,
  `sellerTemplates.service.cjs`/`.repo.cjs`. **Правило:** для файлов
  из этого списка — не полагаться на "маленькая правка, ничего не
  потеряется"; грепать 2-3 маркера прошлых фич перед
  full-file-overwrite. При сборке финального патча — всегда сверять
  diff по количеству/составу файлов с тем, что реально менялось в
  этой сессии, не доверять слепо.
- **Файлы миграций в этом репо НЕЛЬЗЯ считать источником истины про
  реальную схему БД.** Раннера миграций нет, на прод накатывается
  вручную, миграции систематически расходятся с реальностью.
  **Правило: прежде чем полагаться на список допустимых
  значений/структуру таблицы — `\d <table>` на реальной БД, не файл
  миграции**, если вопрос хоть немного важен (тем более
  деньги/чекаут).
- **Express: catch-all/404-обработчик и порядок монтирования
  роутеров.** Если приложение собирается в несколько слоёв
  (`createWebApp()` возвращает `webApp`, затем внешний код
  донавешивает на него ещё роуты) — catch-all должен быть ПОСЛЕДНИМ
  `.use()` на том слое, где реально смонтированы все роуты, иначе он
  либо перехватит донавешенные позже роуты, либо (если повешен на
  внешний `app`, а не на `webApp`) не будет иметь доступа к
  `view engine`, настроенному только на `webApp` — `res.render()`
  внутри упадёт с "No default engine". Тестировать через реально
  собранный полный `app.js`, не изолированный внутренний модуль.
- **SQL: `LEFT JOIN` к таблице с потенциально многими строками на
  одну "главную" (`orders` на `seller_templates`) плодит строки —
  `COUNT(*)`/`AVG()` без `DISTINCT` через такой JOIN считают
  неправильно, если у "главной" сущности больше одной связанной
  строки.** Для подсчётов — `COUNT(DISTINCT id)`. Для средних цен —
  вообще не джойнить таблицу с транзакциями напрямую, использовать
  `EXISTS`-подзапрос (не плодит строк) поверх собственной цены
  сущности.
- **Поиск кириллицы/не-ASCII текста для перевода — не `grep -P`.**
  Ложные срабатывания на многобайтовые UTF-8-символы (`€`, `—`,
  `’`) в некоторых локалях/системах, либо падение с ошибкой на
  синтаксисе `\x{0400}`. Использовать Python с точным
  unicode-диапазоном (`re.findall(r'[\u0400-\u04FF]', content)`).
- **Разные имена ошибки для одного и того же конфликта, брошенные из
  функций-сестёр — повторяющийся источник багов.** При добавлении
  обработки ошибки от функции в `*.repo.cjs`/сервисе — грепать все
  места, где эта функция (и её "родственники" по смыслу) реально
  кидают `new Error(...)`, а не полагаться на то, что один
  проверяемый код покрывает всё семейство похожих ошибок.
- **HTML `<input type="file">` не восстанавливает выбор при
  перерендере страницы после ошибки валидации** — ограничение
  браузера, не баг. Не чинить на уровне кода, иметь в виду при
  диагностике.
- **Проверка реального mount'а, не просто `fs.existsSync()`.**
  Сравнение `st_dev` директории и родителя (`isMountPoint()`) — тот
  же приём, что у Unix-команды `mountpoint`.
- **Решение:** админка встроена в существующее приложение (роль
  `admin`/`superadmin` в общей таблице `users`), не отдельный сайт —
  общие таблицы `users`/`sessions`, стадия MVP.
- **Решение:** визуал админки полностью переиспользует публичный
  дизайн (header/footer/шрифты). Изоляция — только код/данные.
- **Риск:** таблица `users` не создаётся ни одной миграцией в
  `src/db/migrations/` — схема известна только из
  `tests/helpers/migrateDb.cjs`. `orders.amount_cents` в том же
  положении.
