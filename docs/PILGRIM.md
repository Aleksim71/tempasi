## Часть 1.1. Спецификация дашборда `/admin` (согласовано 2026-07-16)

4 KPI-карточки + переключатель периода (1 / 7 / 28 дней, `?period=`):

1. **Пользователи** — общее количество (все, `COUNT(*) FROM users`) +
   дельта = нетто-изменение за период (`created_at` в пределах периода;
   у users нет мягкого удаления, поэтому дельта фактически = кол-во новых
   регистраций, всегда ≥ 0).
2. **Шаблоны** — общее количество **только `status='published'` и
   `deleted_at IS NULL`** (решение: считаем то, что видно в каталоге, не
   черновики) + дельта = нетто (вновь опубликованные минус удалённые за
   период). **Известное ограничение:** переход `published -> draft` без
   удаления записи в дельте не отражается — в схеме нет истории статусов.
   Когда Этап 2 начнёт писать переходы в `admin_audit_log`, дельту можно
   будет считать точно.
3. **Выручка · аренда** (`orders WHERE deal_type='RENT' AND status='paid'`)
   — сумма за период + дельта **в деньгах** относительно предыдущего
   периода такой же длины.

## Часть 2. Правила работы

### Режимы

- **Обсуждение** — просто разговариваем, ничего не меняем в проекте.
- **Работа** — берём одну маленькую цель из плана (Часть 1), доводим до
  конца по шагам ниже, проверяем, отмечаем чекбокс, только потом берём
  следующую.

### Порядок работы над одной целью (обязателен, без исключений)

1. **Сбор информации.** Прежде чем предлагать решение или менять
   код/БД/окружение, Claude собирает всё необходимое по факту (читает
   реальные файлы, миграции, схему БД, конвенции проекта) — не
   предполагает и не додумывает, как "должно быть устроено".
2. **Варианты решения.** На основе собранной информации Claude предлагает
   вариант(ы) решения с плюсами/минусами, привязанными к реальному коду
   (не общими рассуждениями).
3. **Обсуждение и выбор.** Обсуждаем, выбираем вариант вместе.
4. **Реализация.** Только после выбора — патч (файлы/SQL/тесты) в
   `incoming/`.
   Пропускать шаг 1 (сразу писать код по предположению) — нарушение
   процесса, даже если цель кажется тривиальной.

### Изоляция админки (MVP на том же сайте, но с заделом на отделение)

- Код/вьюхи — только в своих namespace'ах: `src/web/routes/admin.*.routes.cjs`,
  `src/web/middleware/require-admin.web.js`, `src/web/views/pages/admin/*`,
  `public/css/pages/admin*.css`.
- **Визуал — исключение из общей идеи изоляции:** header/footer/шрифты
  сознательно общие с публичным сайтом (решение 2026-07-16). Изоляция
  относится к коду/бизнес-логике, не к дизайну.
- **Админка не пишет ad-hoc SQL по таблицам, которыми владеют другие
  модули.** Если нужна операция (например, unpublish шаблона) — она
  добавляется как метод в сервис модуля-владельца (например,
  `sellerTemplates.service.cjs`), а не как отдельный запрос в
  admin-роуте. Бизнес-правила живут в одном месте. **(Начнёт
  действовать с Этапа 2 — в Этапе 1 админка только читает данные для
  дашборда.)**
- Известный заранее компромисс, который не решаем сейчас: авторизация
  админки использует общие `sessions`/`users`. При реальном отделении
  потребуется либо общий session-store (Redis), либо SSO — сейчас это
  не блокер, просто зафиксированный риск на будущее.

### Обмен файлами

```
incoming   <- патчи от Claude (в этом чате: /home/aleksim/Загрузки)
outgoing   <- результаты/логи от пользователя обратно Claude
             (в этом чате: /home/aleksim/workspace/projects/tempasi/Outbox)
archive    <- применённые патчи (история)
```

Проект: `/home/aleksim/tempasi`.

### Формат патча

- Входящий файл — zip, но **не обязательно Python**: это могут быть
  bash/PowerShell-команды, обычные diff/patch-файлы, `.sql`-файлы.
- Обязательная единая точка входа — `run.sh` (bash, под Ubuntu),
  которая применяет всё и пишет лог в `outgoing/`.
- Файловые изменения — предпочтительно как unified diff / `git apply`
  (если проект под git), а не спрятаны внутри произвольного скрипта.
- Изменения в БД — отдельный `.sql`-файл + шаг с бэкапом (`pg_dump`
  нужных таблиц) перед применением + явное подтверждение перед
  деструктивными операциями (UPDATE/DELETE/DROP).
- Тесты можно писать и прогонять как часть патча; вывод — в `outgoing/`.

**Апробировано в этом чате:** `run.sh` умеет откатываться безопасно —
если нет `DATABASE_URL`, нет `pg_dump`, или в `users` находятся роли вне
допустимого набора, миграция не применяется, code-diff при этом уже
может быть применён (он идёт первым и не зависит от БД).

### Правило "Пилигрима"

- Загружается в начале чата.
- Обновляется Claude в конце чата (после завершения задач/уточнения правил).
- Новый чат открывается: либо по достижении естественной точки паузы
  (закрыт этап/подзадача), либо ориентировочно через ~20 сообщений —
  пользователь отслеживает это сам, Claude не считает сообщения
  автоматически.

### Технические детали окружения

- ОС/шелл для запуска патчей: **Ubuntu, bash**.
- Проект под git: **да**, ветка `feat/analytics-kpi-summary`.
- Прямой доступ к БД с рабочей машины: **через `.env` (`DATABASE_URL`)**,
  без отдельно настроенного `psql`-клиента — значит SQL-патчи должны
  подключаться через `DATABASE_URL` из `.env` (например,
  `psql "$DATABASE_URL" -f patch.sql`, если `psql` всё же есть в системе,
  либо через `node`-скрипт на `pg`, который уже используется в проекте).

## Часть 4. Открытые риски и принятые решения

- **НОВЫЙ УРОК (2026-08-04): `node --check` проверяет только синтаксис,
  не то, что нужный export реально существует.** При пересборке файла
  с устаревшей базы (см. следующий пункт) функция `uploadMyAvatarJson`
  вместе с её `require('path')` молча потерялась при правках — файл
  остался синтаксически валидным, `node --check` прошёл зелёным, но
  функция физически отсутствовала, и вызывающий код падал в рантайме
  ("uploadMyAvatarJson is not a function"). **Правило на будущее:**
  если патч добавляет/переносит функцию в `module.exports`, перед
  отправкой — реальный `require()` собранного файла (с заглушками
  недостающих зависимостей при необходимости) и явная проверка
  `typeof mod.functionName === 'function'`, не полагаться на один
  лишь `node --check`.
- **ПОВТОРЯЮЩИЙСЯ РИСК (обновлено 2026-08-04, уже 3-й подтверждённый
  случай): песочница Claude периодически теряет файлы между
  сообщениями чата, а полная перезапись файла на основе устаревшей
  копии молча откатывает уже закоммиченную работу.** Случаи: (1)
  Templates-карточка — потерялись прошлые patchN каталогов; (2)
  `profile.controller.cjs` для Community — потеряна целая функция
  `uploadMyAvatarJson`; (3) `cabinet.pages.routes.cjs` в патче с
  золотым подчёркиванием — откатились `avatar_url`/`public_profile`
  (собирался на свежей распаковке, предшествовавшей Community).
  **Общий паттерн всех трёх:** правка казалась маленькой и
  локальной ("добавить одну строку `activePage`"), поэтому файл
  просто заново распаковывался из `tempasi.zip` вместо запроса
  актуальной копии — а конкретно этот файл к тому моменту уже
  накопил много несвязанных с задачей изменений в других частях.
  **Правило на будущее, ужесточено:** для любого файла с историей
  правок в этой же сессии (не только "если был перерыв") — либо
  запросить свежий `tempasi.zip` перед full-file-overwrite патчем,
  либо (для маленьких точечных правок) использовать точечный
  str_replace/sed по known-anchor тексту вместо полной перезаписи
  файла, чтобы случайно не задеть несвязанный, ранее закоммиченный
  код в том же файле.
- **ВАЖНЫЙ ПОВТОРЯЮЩИЙСЯ УРОК (обновлено 2026-08-02): файлы миграций
  в этом репо НЕЛЬЗЯ считать источником истины про реальную схему
  БД.** Раннера миграций в проекте нет вообще — на прод накатывается
  вручную, файлы миграций систематически расходятся с реальностью.
  Уже минимум 4 подтверждённых случая: `users.role` (Этап 1),
  `category`/`user_profiles` (Templates), `orders.amount_cents`
  (компат-патч в тестовой схеме), и теперь — `cart_items.license`
  (файл миграции разрешает `PU/CU/EL/ML/EX`, реальный `CHECK` на
  проде — `'BUY'/'RENT'/'PU'/'PU:Nd'`, совершенно другой набор).
  Последний случай стоил лишнего круга: сначала "починил" по файлу
  миграции (`license="EX"`), это прошло валидацию приложения, но
  упало на реальном ограничении БД необработанным исключением — хуже
  исходного бага. \*\*Правило на будущее: прежде чем полагаться на
  список допустимых значений/структуру таблицы — попросить `\d
  <table>` на реальной БД, а не читать файл миграции, если вопрос
  хоть немного важен (тем более если речь о деньгах/чекауте).**
