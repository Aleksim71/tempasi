## Часть 2. Правила работы (актуально)

### Режимы

- **Обсуждение** — просто разговариваем, ничего не меняем в проекте.
- **Работа** — берём одну маленькую цель, доводим до конца по шагам
  ниже, проверяем, только потом берём следующую.

### Порядок работы над одной целью (обязателен)

1. **Сбор информации** — реальные файлы/схема БД/конвенции, не
   предположения.
2. **Варианты решения** — привязаны к реальному коду.
3. **Обсуждение и выбор.**
4. **Реализация** — патч (файлы/SQL/тесты).

### Изоляция админки (MVP на том же сайте, задел на отделение)

- Код/вьюхи — только в своих namespace'ах:
  `src/web/routes/admin.*.routes.cjs`,
  `src/web/middleware/require-admin.web.js`,
  `src/web/views/pages/admin/*`, `public/css/pages/admin*.css`.
- Визуал — исключение: header/footer/шрифты сознательно общие с
  публичным сайтом. Изоляция — только код/бизнес-логика.
- Админка не пишет ad-hoc SQL по таблицам других модулей — операция
  добавляется как метод в сервис модуля-владельца.
- Известный компромисс: авторизация админки использует общие
  `sessions`/`users`. При реальном отделении — общий session-store
  (Redis) или SSO. Не блокер сейчас.

### Обмен файлами

```
incoming   <- патчи от Claude (в этом чате: /home/aleksim/Загрузки)
outgoing   <- результаты/логи от пользователя обратно Claude
archive    <- применённые патчи (история)
```

Проект: `/home/aleksim/tempasi`.

### Формат патча

- Единая точка входа — `run.sh` (bash, Ubuntu), применяет всё, пишет
  лог в `outgoing/`.
- Изменения в БД — отдельный `.sql` + `pg_dump`-бэкап + явное
  подтверждение перед деструктивными операциями. Перед CHECK-
  констрейнтами на существующую колонку — сначала `SELECT DISTINCT
  <col> FROM <table>` на реальной БД, констрейнт иначе не
  прикрепится, если есть неожиданное значение.
- **Перед любой full-file-overwrite правкой** — грепнуть целевой файл
  на 2-3 маркера уже известных прошлых фич; если хоть один не найден
  — остановиться, восстановить из сохранённых `patchN` или запросить
  свежий `tempasi.zip`.
- **Патчи с зависимостями друг от друга** — `run.sh` каждого такого
  патча грепает маркер патча-предпосылки в начале и падает с
  понятным ABORT, если его нет. Несколько патчей за сессию подряд по
  одному и тому же файлу — это нормально, не повод сливать всё в
  один патч.
- **Перед вставкой кода с `—`/`€`/эмодзи через `str_replace`** —
  всегда реальный UTF-8-символ, никогда `\uXXXX`-эскейп (инструмент
  задваивает обратный слэш). Безопаснее — строить такие правки через
  `bash_tool`/Python (`content.replace(...)`) вместо `str_replace`,
  если правка длинная или тире/евро много.
- **Реальная проверка, не только `node --check`/`git apply --check`.**
  Почти каждый патч проверяется живым вызовом через
  `supertest`/прямой `require()` с фейковым db/фейковой сессией на
  чистой копии архива в `run.sh`, а не только синтаксисом.
- **Если пользователь под git — источник истины про текущее
  состояние файла это `git diff HEAD -- <path>` /
  `git status --short`, не `sed`/`cat`-дамп в чат.** Терминальный
  копипаст может молча терять пустые строки без потери их в самом
  файле; `git diff` этому не подвержен. Если `git diff HEAD` пустой,
  но текст всё равно выглядит иначе, чем ожидалось — подозревать
  `prettier`/`lint-staged` на pre-commit хуке (переформатирует `.md`
  и другие файлы при коммите), не копипаст; тогда просить файл
  вложением, не текстом в чат.
- **После получения `run.sh`-патча от Claude — коммитить сразу только
  файлы кода/тестов, не диагностические `.diff`/`run.sh`/`outgoing/`**
  (они одноразовые, не для истории репозитория).

### Правило "Пилигрима"

- Загружается в начале чата (`docs/PILGRIM.md`, без даты — всегда
  актуальная точка входа).
- Обновляется Claude в конце чата.
- Периодически архивируется целиком под датой, когда разрастается —
  см. раздел "Архивы" в начале этого файла.
- Новый чат — по достижении естественной паузы или ~20 сообщений,
  пользователь отслеживает сам.

### Технические детали окружения

- ОС/шелл: Ubuntu, bash. Проект под git, ветка
  `feat/analytics-kpi-summary`.
- Доступ к БД: через `.env` (`DATABASE_URL`), `psql` тоже доступен
  напрямую в терминале пользователя.
- Стек: Node.js/Express 5, PostgreSQL, Handlebars (SSR), CJS-модули
  вперемешку с ESM (`.cjs` vs `.js` — смотреть по факту в каждом
  файле; `web.routes.js` и некоторые другие — чистый ESM с
  `import`/`export`, `package.json` имеет `"type": "module"`), git,
  `getPool()` для доступа к БД.
- **Тесты, использующие `await import(...)` для ESM-модулей внутри
  Jest** — обязательно `NODE_OPTIONS=--experimental-vm-modules`, не
  просто `npx jest`. В проекте уже настроено в `npm test`/`npm run
test:db` и в `jest.config.cjs` (`customExportConditions`), но если
  прогонять точечно вручную (например, один тестовый файл) — флаг
  нужно проставлять явно самому: `NODE_OPTIONS=--experimental-vm-modules
npx jest <file> --config ./jest.config.cjs`.
- `TEMPLATE_UPLOAD_DIR` (`/mnt/tempasi/templates`) — sshfs-mount на
  физически отдельную машину ("старичок", `192.168.0.249`), через
  systemd `automount`-юнит (`mnt-tempasi-templates.automount`).

## Часть 4. Устойчивые уроки (актуально, перечитывать каждую сессию)

- **Прежде чем писать текст, который выглядит как факт о продукте
  (в UI, в FAQ, где угодно) — свериться с реальным кодом, а не
  формулировать правдоподобно звучащее.** При написании FAQ для
  Support специально проверил по коду, что "эксклюзивность" реально
  обеспечивается (`normalizeTemplateAvailability` в
  `templates.routes.js` действительно помечает шаблон unavailable),
  и не стал придумывать политику возврата средств от себя — уточнил
  у пользователя явно, это бизнес-решение, а не техническая деталь.
  Написанный вслепую текст в разделе поддержки может разойтись с
  реальным поведением сайта и стать источником реальных жалоб.
- **Не любой существующий, но неиспользуемый актив в репозитории —
  можно/нужно бездумно подключать.** `public/css/custom.css` (824
  строки) содержит нужные классы `.page-intro` и т.п., но также
  переопределения `.site-header` и других глобальных элементов,
  которые нигде не тестировались (сам файл нигде не подключён).
  Вместо risky "просто заимпортить весь файл" — маленький новый CSS
  на уже загруженных токенах (`--c-text`, `--c-muted` и т.д. из
  `core.css`), scoped только под новую фичу.
- **`await import(...)` (ESM dynamic import) внутри Jest-теста не
  работает через голый `npx jest`** — нужен
  `NODE_OPTIONS=--experimental-vm-modules`. Симптом:
  `TypeError: A dynamic import callback was invoked without
--experimental-vm-modules`, легко спутать с более серьёзной
  проблемой. Проверить сначала `package.json`/`jest.config.cjs` на
  готовый npm-скрипт с нужным флагом, прежде чем гонять `npx jest`
  напрямую в песочнице.
- **`try/catch` вокруг всего роута — удобно для fail-safe рендера,
  но тихо хоронит реальные баги без единого следа.** Finance Orders
  джойнился на `LEFT JOIN templates t` — таблицы `templates` нет ни
  в одной миграции (только `seller_templates`), запрос кидал
  `relation "templates" does not exist`, роут ловил исключение в
  `catch (e) { workspaceError = e; }` и рендерил дефолтные нули —
  снаружи выглядело просто как "Own revenue всегда 0.00", а не как
  ошибка. **Правило: если страница с деньгами/данными неожиданно
  показывает нули/пустоту при том, что данные в БД точно есть —
  первым делом временно залогировать `e` в ближайшем catch вокруг
  рендера, а не гадать по коду.**
- **`hbs.registerPartials()` манглит дефисы в именах файлов.** Автоскан
  папки `partials/` по умолчанию заменяет каждый `-` в имени файла на
  `_` (`page-alert.hbs` → зарегистрирован как `page_alert`). Любой
  partial с дефисом в имени нужно ЯВНО перерегистрировать после
  автоскана через `registerPartialSafe('page-alert', content)` в
  `app.web.js`.
- **Когда пользователь мог уже применить более раннюю черновую версию
  патча, чем та, что диффуется — `git apply` слишком хрупкий
  инструмент для дельта-фикса.** Для такого сценария надёжнее
  написать небольшой Python-скрипт, который находит нужный блок **по
  уникальному якорю** через regex с `re.DOTALL` и заменяет весь блок
  целиком заранее подготовленным финальным текстом.
- **Канонический сервис завершения оплаты может быть неполным даже
  для уже существующей, вроде бы работающей фичи.** При добавлении
  новой бизнес-логики, завязанной на "заказ оплачен" — сначала
  проверить, действительно ли она есть в каноническом сервисе, а не
  только в одном из нескольких параллельных путей.
- **`sudo umount -l` (lazy unmount) на autofs-управляемой точке может
  зацепить сам automount-триггер.** Правильная последовательность:
  `sudo umount -l <path>` → `sudo systemctl reset-failed
<name>.automount` → `sudo systemctl restart <name>.automount`.
- **`node --check` проверяет только синтаксис, не то, что нужный

'function'`.

- **Файлы миграций в этом репо НЕЛЬЗЯ считать источником истины про

- **Express: catch-all/404-обработчик должен быть ПОСЛЕДНИМ `.use()`**
  на том слое, где реально смонтированы все роуты. Тестировать через
  реально собранный полный `app.js`, не изолированный модуль.

- **Разные имена ошибки для одного и того же конфликта, брошенные из
