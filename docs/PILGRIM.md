### Инцидент по пути: хрупкость `git apply` при неточной реконструкции чужого состояния

Патч #10-финал (RENT-only) пришлось чинить **трижды**: первая версия
диффа строилась от чистой базы + зависимостей, но пользователь уже
успел применить более раннюю черновую версию той же фичи (с BUY и
старой KPI-строкой) — `git apply --check` падал на несовпадении
контекста. Вторая попытка — Claude реконструировал предполагаемое
"уже применённое" состояние по памяти и собрал дельта-diff от него;
дельта-diff тоже не применился (реконструкция разошлась с реальным
файлом в мелочах — вероятно, пробелы/переносы). **Решение, сработавшее
с первого раза**: полностью отказаться от `git apply` для этого
конкретного фикса и написать `apply.py` — Python-скрипт, который
находит нужную функцию/HTML-блок **по уникальным якорям** (имя
функции, HTML-комментарий-маркер) через regex и заменяет **весь
блок целиком** финальным текстом, не заботясь о том, что было внутри
до этого. Идемпотентен (безопасно перезапускать), явно ABORT'ится,
если якорь не найден вообще. Проверен на намеренно "зашумлённом"
(другое форматирование/лишние пустые строки) тестовом сценарии —
сработал. См. урок ниже.

### Инцидент по пути: sshfs/automount

Live Demo одного шаблона (`lumen-frame`) не открывался — браузер
просто вис. Диагностика: `TEMPLATE_UPLOAD_DIR` смонтирован через

инцидент от собственных действий — см. урок про `umount -l` ниже.

## Часть 2. Правила работы (актуально)

### Режимы

- **Обсуждение** — просто разговариваем, ничего не меняем в проекте.
- **Работа** — берём одну маленькую цель, доводим до конца по шагам
  ниже, проверяем, только потом берём следующую.

### Порядок работы над одной целью (обязателен)

1. **Сбор информации** — реальные файлы/схема БД/конвенции, не
   предположения.
2. **Варианты решения** — привязаны к реальному коду.
3. **Обсуждение и выбор.**
4. **Реализация** — патч (файлы/SQL/тесты).

### Изоляция админки (MVP на том же сайте, задел на отделение)

- Код/вьюхи — только в своих namespace'ах:
  `src/web/routes/admin.*.routes.cjs`,
  `src/web/middleware/require-admin.web.js`,
  `src/web/views/pages/admin/*`, `public/css/pages/admin*.css`.
- Визуал — исключение: header/footer/шрифты сознательно общие с
  публичным сайтом. Изоляция — только код/бизнес-логика.
- Админка не пишет ad-hoc SQL по таблицам других модулей — операция
  добавляется как метод в сервис модуля-владельца.
- Известный компромисс: авторизация админки использует общие
  `sessions`/`users`. При реальном отделении — общий session-store
  (Redis) или SSO. Не блокер сейчас.

### Обмен файлами

```
incoming   <- патчи от Claude (в этом чате: /home/aleksim/Загрузки)
outgoing   <- результаты/логи от пользователя обратно Claude
archive    <- применённые патчи (история)
```

Проект: `/home/aleksim/tempasi`.

### Формат патча

- Единая точка входа — `run.sh` (bash, Ubuntu), применяет всё, пишет
  лог в `outgoing/`.
- Изменения в БД — отдельный `.sql` + `pg_dump`-бэкап + явное
  подтверждение перед деструктивными операциями. Перед CHECK-
  констрейнтами на существующую колонку — сначала `SELECT DISTINCT
  <col> FROM <table>` на реальной БД, констрейнт иначе не
  прикрепится, если есть неожиданное значение.
- **Перед любой full-file-overwrite правкой** — грепнуть целевой файл
  на 2-3 маркера уже известных прошлых фич; если хоть один не найден
  — остановиться, восстановить из сохранённых `patchN` или запросить
  свежий `tempasi.zip`.
- **Патчи с зависимостями друг от друга** — `run.sh` каждого такого
  патча грепает маркер патча-предпосылки в начале и падает с
  понятным ABORT, если его нет. Несколько патчей за сессию подряд по
  одному и тому же файлу — это нормально, не повод сливать всё в
  один патч.
- **Перед вставкой кода с `—`/`€`/эмодзи через `str_replace`** —
  всегда реальный UTF-8-символ, никогда `\uXXXX`-эскейп (инструмент
  задваивает обратный слэш). Безопаснее — строить такие правки через
  `bash_tool`/Python (`content.replace(...)`) вместо `str_replace`,
  если правка длинная или тире/евро много.
- **Реальная проверка, не только `node --check`/`git apply --check`.**
  Эта сессия — хороший пример: почти каждый патч проверялся живым
  вызовом через `supertest`/прямой `require()` с фейковым db/фейковой
  сессией на чистой копии архива в `run.sh`, а не только синтаксисом.
  Особенно важно для платёжного/чекаут-кода (патч #5) — там
  проверялись оба конца цепочки (`completePaidOrder()` изолированно
  и `POST /cart/checkout-all` целиком через HTTP).

### Правило "Пилигрима"

- Периодически архивируется целиком под датой, когда разрастается —

## Часть 4. Устойчивые уроки (актуально, перечитывать каждую сессию)

- **`try/catch` вокруг всего роута — удобно для fail-safe рендера,
  но тихо хоронит реальные баги без единого следа.** Finance Orders
  джойнился на `LEFT JOIN templates t` — таблицы `templates` нет ни
  в одной миграции (только `seller_templates`), запрос кидал
  `relation "templates" does not exist`, роут ловил исключение в
  `catch (e) { workspaceError = e; }` и рендерил дефолтные нули —
  снаружи выглядело просто как "Own revenue всегда 0.00", а не как
  ошибка. Нашли только когда временно воткнули `console.error(e)`
  в catch и прогнали реальный HTTP-запрос — по одним только
  зелёным/красным юнит-тестам это не всплывало, пока новый тест не
  начал проверять конкретные ненулевые суммы. **Правило: если
  страница с деньгами/данными неожиданно показывает нули/пустоту
  при том, что данные в БД точно есть — первым делом временно
  залогировать `e` в ближайшем catch вокруг рендера, а не гадать по
  коду.** Заодно нашли ещё 2 места с тем же паттерном
  (`entitlements.cabinet.repo.cjs`, Profile → Downloads) — не
  тронуты, см. "Известный долг".
- **`hbs.registerPartials()` манглит дефисы в именах файлов.** Автоскан
  папки `partials/` по умолчанию заменяет каждый `-` в имени файла на
  `_` (`page-alert.hbs` → зарегистрирован как `page_alert`). Любой
  partial с дефисом в имени, который во вьюхах вызывается через
  `{{> page-alert}}` (с дефисом), нужно ЯВНО перерегистрировать после
  автоскана через `registerPartialSafe('page-alert', content)` в
  `app.web.js` — паттерн уже применён для `template-card.v2`/
  `site-header`/`icon-*`, просто нужно не забывать повторять его для
  каждого нового хайфенированного partial. Без этого — ошибка вида
  `The partial X could not be found` появляется не сразу при
  разработке (пока сервер не перезапущен), а неожиданно после
  рестарта — легко спутать с проблемой кэша.
- **Когда пользователь мог уже применить более раннюю черновую версию
  патча, чем та, что диффуется — `git apply` слишком хрупкий
  инструмент для дельта-фикса.** Реконструкция чужого "уже
  применённого" состояния по памяти для построения git-diff почти
  гарантированно разойдётся с реальностью в мелочах (пробелы,
  переносы строк) и `git apply --check` откажется применяться — даже
  если по смыслу всё совпадает. Для такого сценария надёжнее написать
  небольшой Python-скрипт, который находит нужный блок **по
  уникальному якорю** (имя функции, HTML-комментарий-маркер) через
  regex с `re.DOTALL` и заменяет весь блок целиком заранее
  подготовленным финальным текстом — не заботясь о том, что было
  внутри. Такой скрипт по конструкции идемпотентен (безопасно
  перезапускать) и не ломается на мелких расхождениях контекста —
  единственное требование — чтобы сам якорь физически существовал в
  файле.
- **Канонический сервис завершения оплаты может быть неполным даже
  для уже существующей, вроде бы работающей фичи.** `completePaidOrder()`
  — единственная точка, через которую ДОЛЖНЫ проходить все способы
  завершить RENT (одиночная покупка, корзина, будущий вебхук) — не
  создавала `order_case_assignments` вообще нигде. Фича "аренда
  попадает в кейс" работала только через отдельную, не до конца
  канонич­ную ветку (`demoCompleteCartCheckout`, которая
  переизобретает завершение оплаты с нуля). При добавлении новой
  бизнес-логики, завязанной на "заказ оплачен" — сначала проверить,
  действительно ли она есть в каноническом сервисе, а не только в
  одном из нескольких параллельных путей, которые к нему исторически
  не свелись.
- **`sudo umount -l` (lazy unmount) на autofs-управляемой точке может
  зацепить сам automount-триггер, а не только текущее
  fuse-соединение.** После этого юнит `<name>.automount` уходит в
  `failed`-состояние и НЕ переподнимается сам при следующем обращении
  к папке — `systemctl restart` без предварительного `systemctl
reset-failed` тоже не поможет, если юнит именно failed (не просто
  inactive). Правильная последовательность для зависшего sshfs-mount
  через autofs: `sudo umount -l <path>` (или `fusermount -uz`) →
  `sudo systemctl reset-failed <name>.automount` → `sudo systemctl
restart <name>.automount` → обращение к папке триггерит новый
  реальный mount.
- **`node --check` проверяет только синтаксис, не то, что нужный
  export реально существует.** Если патч добавляет/переносит функцию
  в `module.exports` — перед отправкой реальный `require()`
  собранного файла (с заглушками зависимостей при необходимости) и
  явная проверка `typeof mod.functionName === 'function'`.
- **ПОВТОРЯЮЩИЙСЯ РИСК: песочница Claude периодически теряет файлы
  между сообщениями чата, полная перезапись файла на основе
  устаревшей копии молча откатывает уже закоммиченную работу.**
  Особенно уязвимые файлы (накопили больше всего несвязанных правок
  за сессии): `admin.pages.routes.cjs`, `cabinet.pages.routes.cjs`,
  `analytics.cabinet.service.cjs`, `space-my-templates.hbs`,
  `space-cases.hbs`, `templates.routes.js`,
  `sellerTemplates.service.cjs`/`.repo.cjs`. **Правило:** для файлов
  из этого списка — не полагаться на "маленькая правка, ничего не
  потеряется"; грепать 2-3 маркера прошлых фич перед
  full-file-overwrite. При сборке финального патча — всегда сверять
  diff по количеству/составу файлов с тем, что реально менялось в
  этой сессии, не доверять слепо.
- **Файлы миграций в этом репо НЕЛЬЗЯ считать источником истины про
  реальную схему БД.** Раннера миграций нет, на прод накатывается
  вручную, миграции систематически расходятся с реальностью.
  **Правило: прежде чем полагаться на список допустимых
  значений/структуру таблицы — `\d <table>` на реальной БД, не файл
  миграции**, если вопрос хоть немного важен (тем более
  деньги/чекаут).
- **Express: catch-all/404-обработчик и порядок монтирования
  роутеров.** Если приложение собирается в несколько слоёв
  (`createWebApp()` возвращает `webApp`, затем внешний код
  донавешивает на него ещё роуты) — catch-all должен быть ПОСЛЕДНИМ
  `.use()` на том слое, где реально смонтированы все роуты.
  Тестировать через реально собранный полный `app.js`, не
  изолированный внутренний модуль.
- **SQL: `LEFT JOIN` к таблице с потенциально многими строками на
  одну "главную" плодит строки** — `COUNT(*)`/`AVG()` без `DISTINCT`
  через такой JOIN считают неправильно. Для подсчётов — `COUNT(DISTINCT
id)`. Для средних цен — `EXISTS`-подзапрос (не плодит строк) поверх
  собственной цены сущности, не джойнить таблицу с транзакциями
  напрямую.
- **Поиск кириллицы/не-ASCII текста для перевода — не `grep -P`.**
  Ложные срабатывания на многобайтовые UTF-8-символы (`€`, `—`,
  `’`) в некоторых локалях/системах, либо падение с ошибкой на
  синтаксисе `\x{0400}`. Использовать Python с точным
  unicode-диапазоном (`re.findall(r'[\u0400-\u04FF]', content)`).
- **Разные имена ошибки для одного и того же конфликта, брошенные из
  функций-сестёр — повторяющийся источник багов.** При добавлении
  обработки ошибки от функции в `*.repo.cjs`/сервисе — грепать все
  места, где эта функция (и её "родственники" по смыслу) реально
  кидают `new Error(...)`, а не полагаться на то, что один
  проверяемый код покрывает всё семейство похожих ошибок.
- **Поля с ценой/суммой в объекте, собранном из SQL-строки — сверять
  реальное имя колонки и единицу измерения (центы vs евро), а не
  доверять правдоподобно звучащему имени поля в коде-потребителе.**
  `normalizeCaseRentRow()` тихо ломалась месяцами именно так — искала
  `*_price_eur`-поля, которых не существовало, вместо реального
  `price_rent_cents`.
- **HTML `<input type="file">` не восстанавливает выбор при
  перерендере страницы после ошибки валидации** — ограничение
  браузера, не баг. Не чинить на уровне кода, иметь в виду при
  диагностике.
- **Проверка реального mount'а, не просто `fs.existsSync()`.**
  Сравнение `st_dev` директории и родителя (`isMountPoint()`) — тот
  же приём, что у Unix-команды `mountpoint`.
- **Решение:** админка встроена в существующее приложение (роль
  `admin`/`superadmin` в общей таблице `users`), не отдельный сайт —
  общие таблицы `users`/`sessions`, стадия MVP.
- **Решение:** визуал админки полностью переиспользует публичный
  дизайн (header/footer/шрифты). Изоляция — только код/данные.
- **Риск:** таблица `users` не создаётся ни одной миграцией в
  `src/db/migrations/` — схема известна только из
  `tests/helpers/migrateDb.cjs`. `orders.amount_cents` в том же
  положении.
